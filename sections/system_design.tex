\section{System Design}

\subsection{How It All Fits Together}
We designed the system as a pipeline that moves data through four main stages. Raw public information goes in, and actionable design recommendations come out. Each stage hands off to the next, and the whole thing is built to be modular—meaning you can swap out pieces without rebuilding everything from scratch.

Here's the flow:
\begin{enumerate}
\item \textbf{Data Collection}: We pull in demand signals from several public sources—Google Trends for search interest, Kaggle datasets for user reviews, and app metadata from various repositories.
\item \textbf{Preprocessing}: The raw data gets cleaned up, normalized, and organized into tidy time-series formats that the forecasting models can actually work with.
\item \textbf{Forecasting}: We run multiple models (Exponential Smoothing, ARIMA, Linear Regression) to generate predictions about future demand for specific features.
\item \textbf{Decision Framework}: The forecasts get translated into concrete suggestions—which features to prioritize, how to allocate resources, when to launch updates.
\end{enumerate}

Data flows one way through the pipeline, from collection to recommendations. We also built in feedback loops so we can refine the models over time based on how well their predictions hold up.

\subsection{Breaking Down the Components}

\subsubsection{Data Collection Module}
This is where everything starts. The module handles three main data sources:
\begin{itemize}
\item \textbf{Google Trends Scraper}: Grabs monthly search interest data for specific Notion features. Want to know how often people searched for "Notion AI" last month? This is where that comes from.
\item \textbf{Review Dataset Parser}: Processes user reviews from Kaggle datasets, extracting ratings, timestamps, and the actual text of what people wrote.
\item \textbf{Metadata Aggregator}: Collects supplementary info like app installation counts, version release histories, and rating distributions.
\end{itemize}

Everything gets timestamped and stored in a consistent format. The module also handles the annoying realities of working with external APIs—rate limits, random failures, retries—so the data collection stays reliable.

\subsubsection{Preprocessing Module}
Raw data is messy, so this module cleans it up before anything else happens:
\begin{itemize}
\item \textbf{Cleaning}: Duplicate entries get removed, missing values get handled (usually through interpolation or carrying forward the last known value), and statistical outliers get flagged.
\item \textbf{Feature Extraction}: We use natural language processing to scan review text and pull out mentions of specific features. How many times did people mention "templates" this month? This tells us.
\item \textbf{Sentiment Scoring}: Reviews get sentiment scores so we know whether users sound happy, frustrated, or neutral about particular features.
\item \textbf{Time-Series Construction}: Everything gets organized into monthly series for each feature—search interest, sentiment, mention counts.
\item \textbf{Normalization}: Since different metrics are on different scales, we normalize values so we can compare apples to apples across features.
\end{itemize}

\subsubsection{Forecasting Engine}
This is the analytical core. We don't rely on a single model because different models have different strengths:
\begin{itemize}
\item \textbf{Exponential Smoothing}: Great for catching short-term shifts. If something spiked last month, this model notices quickly.
\item \textbf{ARIMA}: Better for long-term patterns—seasonality, cycles, trends that unfold over many months.
\item \textbf{Linear Regression}: Helps us incorporate outside factors. Did a competitor just launch something similar? Is there buzz in the news? Regression can factor that in.
\end{itemize}

Each model produces its own forecast, and then we blend them using an ensemble approach. Models that have been more accurate historically get more weight in the final prediction. We also generate confidence intervals so decision-makers know how certain (or uncertain) each forecast is.

\subsubsection{Design Decision Framework}
Forecasts are just numbers until you do something with them. This module takes the predictions and generates practical recommendations:
\begin{itemize}
\item \textbf{Feature Prioritization}: Ranks features based on predicted demand growth, current user sentiment, and strategic importance.
\item \textbf{UI/UX Suggestions}: For high-demand features, recommends improvements like better discoverability or simplified workflows.
\item \textbf{Resource Planning}: Suggests how to distribute engineering effort based on where demand is heading.
\item \textbf{Release Timing}: Identifies when demand peaks are expected so launches can be timed accordingly.
\end{itemize}

The logic is rule-based with threshold triggers. If predicted demand growth exceeds a certain level and sentiment is positive, the feature gets flagged as high priority. It's not magic, but it's systematic.

\subsubsection{User Interface Module}
All of this needs to be usable by actual humans—not just data scientists staring at terminal output. The UI provides:
\begin{itemize}
\item \textbf{Dashboard Views}: High-level metrics and trend visualizations so stakeholders can see what's happening at a glance.
\item \textbf{Feature Drill-downs}: Detailed time-series charts for individual features, with sentiment overlays and model comparison widgets.
\item \textbf{Recommendations Panel}: Prioritized suggestions, estimated effort, and suggested launch windows—all derived from the forecasting pipeline.
\item \textbf{Export Options}: CSV and JSON exports plus printable reports for offline review or sharing with people who prefer spreadsheets.
\end{itemize}

We intentionally kept the UI decoupled from the forecasting engine. That way, we can redesign the interface without touching the analytics logic, and vice versa.

\subsection{Technology Choices}

\subsubsection{Languages}
\begin{itemize}
\item \textbf{Python}: The workhorse for data processing, statistical modeling, and forecasting. Python's ecosystem of data science libraries made it the obvious choice.
\item \textbf{SQL}: For structured storage and querying of time-series data when needed.
\end{itemize}

\subsubsection{Libraries and Frameworks}
\begin{itemize}
\item \textbf{pandas}: Data manipulation and time-series handling.
\item \textbf{NumPy}: Number crunching and array operations.
\item \textbf{statsmodels}: Our go-to for ARIMA and Exponential Smoothing implementations.
\item \textbf{scikit-learn}: Linear regression, preprocessing utilities, and evaluation metrics.
\item \textbf{NLTK and spaCy}: Natural language processing for extracting feature mentions from review text.
\item \textbf{TextBlob and VADER}: Sentiment analysis—quick and practical for scoring how positive or negative reviews sound.
\item \textbf{matplotlib and seaborn}: Plotting and visualization.
\item \textbf{pytrends}: Python wrapper for the Google Trends API.
\end{itemize}

\subsubsection{Data Sources and Storage}
\begin{itemize}
\item \textbf{Google Trends API}: Search interest time-series.
\item \textbf{Kaggle Datasets}: User reviews and feedback collections.
\item \textbf{CSV/JSON Files}: Lightweight storage for collected and processed data—easy to version and inspect.
\item \textbf{SQLite / PostgreSQL}: Relational database options for larger or more structured deployments.
\end{itemize}

\subsubsection{Development Tools}
\begin{itemize}
\item \textbf{Jupyter Notebooks}: Interactive exploration and prototyping.
\item \textbf{Git / GitHub}: Version control and collaboration.
\item \textbf{VS Code / PyCharm}: Code editing.
\item \textbf{pytest}: Testing framework for validation.
\end{itemize}

\subsubsection{Why These Choices?}
We picked this stack because it's accessible, flexible, and well-supported:
\begin{itemize}
\item \textbf{Accessible}: Everything is open-source. No expensive licenses required.
\item \textbf{Flexible}: The modular design means you can swap in different forecasting algorithms or data sources without rewriting the whole system.
\item \textbf{Scalable}: The pipeline can handle small case studies or scale up to larger datasets if needed.
\item \textbf{Community Support}: These are widely-used tools with active communities, plenty of documentation, and easy-to-find help when things go wrong.
\end{itemize}
